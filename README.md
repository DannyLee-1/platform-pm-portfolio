## 포트폴리오 맵

| 구분 | ① ORBIT | ② 임산부 불빛 배려석 |
|---|---|---|
| **프로젝트 유형** | 초기 팀빌딩 **양면 매칭 플랫폼** | 행동을 바꾸는 **공공 서비스·운영 설계** |
| **핵심 문제** | 수요자와 공급자 사이의 정보 비대칭 | 필요한 사람의 이용 신호가 보이지 않음 |
| **주요 사용자** | 아이디어 보유자 ↔ 합류 희망자 | 임산부 ↔ 일반 승객 ↔ 운영기관 |
| **PM의 핵심 판단** | 단순 추천보다 신뢰 형성과 합류 리스크 해소가 우선 | 개인의 배려가 아닌 신호 체계의 문제로 재정의 |
| **검증한 역량** | 양면 여정, 매칭, 신뢰 장치, 전환 퍼널, MVP | 이해관계자 조율, 행동 유도, 운영 정책, 예외 처리 |
| **결과** | 핵심 여정이 작동하는 MVP 배포 | 서울시 아이디어풀 등재 과제 선정 |

## ① ORBIT — 초기 팀빌딩 양면 매칭 플랫폼

### 문제와 해결

| Before: 기존 시장의 공백 | ORBIT의 해결 방식 | After: 사용자의 도착점 |
|---|---|---|
| 초기 창업자는 필요한 역할을 정의하기 어려움 | 한 줄 아이디어를 역할과 작업으로 구체화 | 누구와 무엇을 만들지 이해 |
| 팀원은 프로젝트의 신뢰도를 판단하기 어려움 | 결과물 검증·아이디어 보호·질문과 응답 제공 | 합류 전에 신뢰와 적합도 확인 |
| 역할·기여·보상 조건이 모호함 | 궁합 공개 후 합류 조건을 명시적으로 합의 | 실행 가능한 팀으로 전환 |

### 양면 사용자 구조

| 수요자: 아이디어 보유자 | ORBIT이 줄이는 마찰 | 공급자: 합류 희망자 |
|---|---|---|
| 필요한 역할을 모름 | 아이디어 → 역할·작업 변환 | 프로젝트 정보가 부족함 |
| 적합한 팀원을 찾기 어려움 | 검증된 후보와 선택 근거 제공 | 자신의 실력과 의향을 증명해야 함 |
| 합류 조건을 정하기 어려움 | 질문·궁합·합의 구조 제공 | 보상과 기여 범위를 확인해야 함 |

### 핵심 전환 퍼널

```mermaid
flowchart LR
    A[아이디어 입력] --> B[프로젝트 생성]
    B --> C[후보 선택]
    C --> D[초대]
    D --> E[응답]
    E --> F[궁합 확인]
    F --> G[합류 합의]
```

| 설계 관점 | 적용한 제품 결정 |
|---|---|
| **MVP 우선순위** | 한 역할·한 후보·한 합의 흐름을 먼저 끝까지 연결 |
| **신뢰 형성** | 결과물 검증, 아이디어 보호 동의, 답변 후 궁합 공개 |
| **운영 정책** | 초대 유효기간, 거절, 재생성 제한, 상세 프로필 공개 시점 |
| **사용자 분기** | 요구사항과 선보수가 확정된 사용자는 외주가 적합하다고 안내 |
| **책임 범위** | ORBIT은 합류 합의까지 지원하고 이후 협업·정산은 당사자 책임으로 구분 |

### 역할과 구현 범위

| 항목 | 내용 |
|---|---|
| **프로젝트 구성** | 부트캠프 3인 팀 프로젝트 |
| **담당 역할** | 문제 정의와 서비스 기획 리드 |
| **수행 범위** | 사전 설문 → PRD → IA → User Flow → 화면·정책 설계 → MVP 배포 |
| **구현 기능** | 회원가입·로그인, 프로젝트 생성, 후보 선택, 초대·응답, 궁합 확인, 합류 합의 |
| **데이터 처리** | 프로젝트·질문·답변·궁합·합의 레코드를 단계별 저장 |
| **검증 범위** | 추천 결과와 데모 지표는 제품 가설 검증용 시나리오이며 실제 운영 성과가 아님 |

## ② 임산부 불빛 배려석 — 행동을 바꾸는 운영·정책 설계

| 단계 | 핵심 내용 |
|---|---|
| **관찰** | 일반 승객은 눈치 때문에 좌석을 비워두고, 임산부는 이용 의사를 알리기 어려움 |
| **문제 재정의** | 시민의 배려 부족 → **수요 신호가 보이지 않는 시스템 문제** |
| **해결 방식** | 버튼과 불빛으로 필요한 순간에만 이용 의사를 전달 |
| **운영 설계** | 제작 비용, 유지관리 주체, 악용 방지, 민원 가능성 검토 |
| **결과** | 심사 대상 중 유일하게 심사위원 전원 적격 판정 · **서울시 아이디어풀 등재 과제 선정** |

이 사례는 특정 공공 도메인보다, 여러 참여자의 행동과 운영 조건을 함께 설계하는 플랫폼 PM 역량을 보여줍니다.

## 역량별 증거

| PM 역량 | ORBIT에서의 증거 | 배려석에서의 증거 |
|---|---|---|
| **문제 정의** | 사람 추천이 아닌 정보 비대칭과 합류 리스크로 정의 | 배려 부족이 아닌 보이지 않는 수요 신호로 정의 |
| **사용자 이해** | 수요자·공급자의 진입과 의사결정 여정 분리 | 임산부·승객·운영기관의 요구 구분 |
| **우선순위** | 핵심 합류 퍼널에 MVP 범위 집중 | 가장 단순한 버튼·불빛 신호에 집중 |
| **운영 설계** | 유효기간·거절·공개 시점·책임 범위 명시 | 유지관리·악용·민원 등 예외 상황 검토 |
| **실행력** | 문서, 프로토타입, 데이터 저장, 배포까지 완결 | 제안서 작성과 심사 통과까지 단독 수행 |
